# 06: Advertising and one Connection

Spec: `.scratch/ble-webapp/spec.md` (Bluetooth, Serial markers). Glossary: Connection, Central.

**What to build:** After the watchdog is armed the board enables Bluetooth and advertises as `XIAO-C6-LED` with the NUS service UUID; it accepts one Connection, stops advertising while it exists, reports the negotiated MTU, and advertises again when the Connection ends. ATT MTU raised to 247. The Harness proves each step as a Central.

**Blocked by:** 04, 05

**Board:** required

**Status:** ready-for-agent

- [x] Boot prints `[BLE] advertising name=XIAO-C6-LED` after `[WDT] armed`.
- [x] The Harness finds the board by name and NUS UUID, connects; the board prints `[BLE] connected` and `[BLE] mtu=<n>`; a second scan while connected does not see the board.
- [x] The Harness disconnects; the board prints `[BLE] disconnected reason=<r>` and `[BLE] advertising ...` again; the Harness reconnects.
- [x] Heap and thread stack headroom measured (thread analyzer in a scenario build) with Bluetooth running; any Kconfig raised is recorded in board-notes with the measurement.
- [x] Harness Checks for all of the above; red path shown for at least one.

- Modules and testing calls: no firmware module here gets a host test (Bluetooth callbacks are glue, proven on the board; the spec's Testing Decisions lists none for this ticket). The Harness Check logic added to `tools/verify/checks.py` (advertising after the watchdog, connected + mtu, silence while connected, disconnected + advertising again) is host-tested in `tools/verify/test_checks.py` (spec: Harness Check logic gets `unittest`); `verify.py`, `central.py` and `BackgroundCapture` are glue.
- Where the spec was silent: (1) `[BLE] disconnected reason=0x<rr>` prints the HCI reason in hex; the Harness expects 0x13 (remote user terminated) for its own disconnect. (2) `[BLE] mtu=<n>` prints `MIN(tx, rx)` of the ATT MTU callback, which also fires with 23 at connection setup; the Harness expects exactly 247 (BlueZ asks for more than 247). (3) Advertising data: name in the advertising PDU, the 128-bit NUS UUID in the scan response (both do not fit 31 bytes); an active scan sees both. (4) Advertising restarts from the `recycled` connection callback (with `BT_MAX_CONN=1` the object is still busy in `disconnected`), at most 5 failures in a row, then it stays off; extra markers `[BLE] advertising failed err=<n>` and `[BLE] start failed err=<n>` report failures. (5) Advertising interval is `BT_LE_ADV_CONN_FAST_1` (100 to 150 ms). (6) The supervision-timeout request above (spec silent on connection parameters). (7) "As soon as" is bounded to 1 s in the Check. (8) Harness adds `BackgroundCapture` (console capture in a thread while the Central runs) and `stop_event` in `console.capture`.
