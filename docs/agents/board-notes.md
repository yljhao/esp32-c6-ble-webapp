# Board notes

Platform knowledge that outlives a session. Two layers: the **card** below is what every session reads first and is kept current (rewrite a line when a fact changes, never stack history); the **evidence log** under it is dated and append-only, read when a card line needs its reason. `implement` reads the card before its first build, and before finishing rewrites any card line that changed and appends its evidence to the log.

A ticket's `Board:` line is a permission, not a schedule: `required` lets the implementer flash, reset, capture serial, drive the probe, or stage the PC network; `none` forbids all of that, including driving the board through the network. Either way, one actor touches the board at a time.

## Every session

One line each, always current. This is the whole file for most sessions. A card line is one sentence: the command, or the fact. It never carries a measurement, a timing, a list of checks, or a date; those go under the evidence log with a dated heading, and the card line may say "see log: <heading>". A card longer than 25 lines, or a line longer than 200 characters, is moved to the log before the session ends.

- Board: Seeed Studio XIAO ESP32-C6, Zephyr target `xiao_esp32c6/esp32c6/hpcore`, Zephyr 4.4.2 at `~/zephyrproject/zephyr`, SDK `~/zephyr-sdk-1.0.1`.
- Port: `/dev/ttyACM0` (USB-Serial/JTAG `303a:1001`), 115200.
- Flash: `west flash -d build` day to day, `./build.sh flash` (pins `--chip esp32c6`) for the Harness and acceptance; both verified here; never `--no-reset`, `--sysbuild`, MCUboot (ADR-0003).
- Reset: `.venv/bin/python tools/board/reset.py` (RTS pulse through USB-Serial/JTAG, reads the ROM banner, port stays; see log: Reset method).
- Capture: `./build.sh serial [SECONDS] [--expect REGEX]` resets, captures with timestamps, exits 1 on a missing marker; `./build.sh console` skips the reset (see log: Capture command).
- Test: `./build.sh test` = twister on `native_sim/native/64`, the esptool guard test and `test-tools`; `./build.sh test-tools` = the `tools/verify` Python unittests alone (no board, BT or serial).

### Board and chip

- 2026-09-30 (inherited from `esp32-c6-wifi-vpn-mqtt-exam-2`, verified there 2026-09-13): Seeed Studio XIAO ESP32-C6, SoC ESP32-C6 (RISC-V), esptool `chip_id` 13. Built-in ceramic antenna; do NOT enable `CONFIG_XIAO_ESP32C6_EXT_ANTENNA`.

### Ticket 08 Shell link command restriction

- 2026-09-30: the Zephyr shell has no per-instance command set. `shell_set_root_cmd()` (`subsys/shell/shell_utils.c`) loops over every shell instance and sets `ctx->selected_cmd`, so it changes the serial shell too (read from the source). `ctx->selected_cmd` is per instance, but setting it only turns on select mode (the first word is looked up under that command), and an unknown command still prints shell text (`<cmd>: command not found`, help, `-h` output), not an `ERR ` line. Rejected.
- Chosen: an allow-list in the Shell link's own transport (`src/link_filter.c`, host suite `tests/link_filter`). `transport_read()` on the shell thread takes each complete queued line, judges it with `link_filter_line()`, hands the shell only a line rebuilt from its words (single spaces, one `\n`), and answers a refused line with `ERR command not allowed` itself; an empty line is dropped silently. Allowed: `led set ...` and `led get ...`. Refused: everything else, and any line with a byte outside 0x20..0x7e (a `\r` inside a line is Enter to the shell, so `led get\rkernel reboot` would have run both), a `"` `'` `\\` `*` `?` in a word, a `-h` or `--help` word, or more than 8 words. The line is rebuilt so the shell never sees the Central's own bytes: no tab completion, escape sequence, history key or quoting reaches it. The serial shell has no filter and keeps every command.
- "Read-only status commands" (spec) is realised as `led get` only: ADR-0001 says the Shell link has never a kernel or device command, and the only other status commands this build has are `kernel version|uptime|...` (there is no top-level `version` in Zephyr 4.4.2's shell; `kernel version` printed `Zephyr version 4.4.2` and `kernel uptime` printed `Uptime: <n> ms` in the first version of this ticket, which allowed them). A later application status command goes into `allowed()` in `link_filter.c`.
- Board results (final image MD5 `c44567cca189da4637cb7c594b7f7e3b`, 541808 bytes, Harness 44 checks): `kernel reboot` over the Shell link answered `ERR command not allowed`, no `[BOOT]` and no ROM banner in the 5.5 s that followed, and the same Connection then answered `led get` with `LED 128`; 13 further inputs (`kernel reboot cold`, `kernel version`, `kernel uptime`, `help`, `device list`, `kernel threads`, `debug hang`, bare `led`, `led set -h`, `  kernel   reboot  `, `led get\rkernel reboot`, `led get` + ESC `[A`, `led` TAB `get`) each gave exactly one `ERR command not allowed` and nothing else, no reset, `led get` still `LED 128`. `kernel reboot` typed on the serial shell gave `[BOOT] reason=software` 2.1 s after the command (`rst:0xc (SW_CPU)`). The console logs the 1st, 2nd, 4th, 8th ... refusal (`shell_nus: commands refused on the Shell link: <n> so far`) so a Central cannot flood the log.
- Wire contract effect: every line a Central writes now gets exactly one `LED <n>` or `ERR ` reply. A bare `led`, `led set -h` and any unknown command used to print shell text (ticket 07 note); they now give `ERR command not allowed`. Nothing changed for `led set` / `led get` with a value, and the stream still holds only replies and Heartbeats.
- Red path on the board: a scratch build with `allowed()` returning true (`build-redfilter`, removed) made the Harness print `FAIL ... kernel reboot is refused ... (no reply line; board reset (ROM banner) at +6.2s)`, `RESULT: FAIL (39/42 checks)`; production was then rebuilt and re-flashed.
- Thread analyzer (`analyze.conf` build, full Harness run 46/46 on the first version of the filter): `shell_nus` peaked at 1344 of 2048 (65 %, ticket 07: 1312), `shell_uart` 612, `main` 1632 of 3072; heap `max_allocated` 21120, unchanged. The later review changes (a static line buffer, no `kernel` branch) do not add stack. The analyze build was removed and production re-flashed.
- Host suite `tests/link_filter`: 11 cases (allow-list, refusals, `\r` smuggling, control bytes, shell syntax, word limit, spacing, empty lines, unterminated line).

### Ticket 09 Heartbeat

- 2026-09-30 design: `src/heartbeat.c` (pure counter and encoder, host suite `tests/heartbeat`, 13 cases) is driven by the main loop, which sleeps until the next Heartbeat is due (never more than 1 s), feeds the watchdog on every pass and calls `heartbeat_link_post(seq)`. That only puts the number into a 3-entry `k_msgq` with `K_NO_WAIT` (a full queue drops the oldest entry and the loop prints `[HB] link stalled: <n> stale heartbeat(s) dropped` at the 1st, 2nd, 4th, 8th ... drop). A sender thread (`heartbeat_sender`, priority 10) encodes the line with `uptime_ms` taken at send time and hands it to `shell_nus_notify()`, which takes the shell transport's TX lock, so a Heartbeat and a reply are whole lines in the stream. The line never passes `link_filter` or `transport_read`. Nothing is sent to a Central that has not subscribed (`bt_nus_send` returns `-EINVAL`/`-ENOTCONN`, dropped silently).
- Thread analyzer (`analyze.conf` build, one Connection receiving Heartbeats and `led get`s): `heartbeat_sender` 640 of 2048 (31 %), `shell_nus` 1328 of 2048, `shell_uart` 504 of 2048, `main` 1680 of 3072, `BT RX WQ` 680 of 1200, `sysworkq` 564 of 1024. The analyze build was removed and production re-flashed.
- Stall proof (`./verify.sh --stall`, debug image: `debug stall` makes the sender stop inside `shell_nus_notify()` holding the TX lock, as a stuck `bt_nus_send()` would): no reset in 29.0 s after the stall marker, `[HB] seq=10..30` kept coming, 16 stale heartbeats reported dropped, `RESULT: PASS (18/18)` including the production restore. Red path: a scratch main loop that also entered the stall point made the Check print `FAIL ... board reset at +4.2s after the stall`, `RESULT: FAIL (17/18)`; source reverted and production re-flashed.
- Cadence facts (measured): the board's `uptime_ms` step is exactly 1000 ms in every run and the console `[HB] seq=10/20/30/40` lines are 10.0 s apart, so the board's period is exact. The PC sees the lines quantised to the 45 ms connection interval (0.945 to 1.080 s in a good period) and, in bad periods of this PC's radio, 1.2 to 2.4 s late for a few lines in a row. Five 25 s probes in a good period (half of them with `led get` traffic) gave 0 of 120 intervals outside 1 +- 0.2 s.
- Radio episodes: on 2026-09-30 between about 06:05 and 08:00 this PC's Bluetooth link was unreliable for whole stretches (`reason=0x08` supervision timeouts, `failed to discover services`, GATT `Unlikely Error` at connect, replies missing). The image of ticket 08, built in a scratch worktree, failed the same way in 4 of 4 Harness runs during such a stretch (and passed 5 of 5 in a good one), so it is not the Heartbeat. `bluetoothctl devices` shows a connected MX Master 3 (BLE mouse) on the same adapter; an interference or scheduling clash with it is a guess, not shown. The Harness now repeats a failed connect (3 tries, printed as `harness: connect attempt <n> failed`) and repeats a Heartbeat window that fails only on the PC clock while the board's `uptime_ms` spacing is exact and no line came more than 3 s after its predecessor (the detail says `link jitter` and the window number).
- Duty readback: the 2 ms window holds about 40.3 periods, so a plain sample count can be off by up to a period in 40 (1.25 %); after the Heartbeat change the Shell link's `led set 128` read 51.3 % (window phase) in 4 of 5 runs and failed the reference tolerance 49 to 51 %. `duty_readback_compute()` now takes the low fraction over whole periods (first to last edge into the same level, plain count when the window holds less than one period); host suite +3 cases; the readbacks since then read 50.0 to 50.5 %.
- Also fixed: a sequence-point warning in `shell_nus.c` (`++refused & (refused - 1)`) from ticket 08.
- Board results (production image MD5 `e7b2ab427aece2ffc27bb5f84b9bb4fc`, 542672 bytes, flash 13.4 %, Harness 50 checks, 88 s): 11 Heartbeats seq 14..24 consecutive at 0.945 to 1.036 s while 9 `led get` / `led set 128` replies arrived whole between them (no other line kind, 21 lines, 420 bytes); after a 5 s disconnect the first seq was 33 after 24 (9 higher after 9.00 s of PC time: the 5 s away plus about 4 s to scan, connect and subscribe); console `[HB] seq=20/30/40` matched the Shell link numbers; after `kernel reboot` on the serial shell the first seq was 2 (uptime_ms 48655 to 5702). The first Heartbeat of a boot is sent about 3.7 s after the reset (the counter starts when the main loop starts).
- Host suite `tests/heartbeat`: seq 0 at boot, +1 per second with no drift, keeps advancing with time when nobody listens (the counter has no listener input), a missed period is consumed not queued, boot resets, wrap at 2^32, wait time, marker every tenth, encoding at the maximum values (53 bytes with the newline, one byte short returns -1).
- The `[HB] seq=N` marker follows `seq % 10 == 0`, so a late pass that jumps over a multiple of 10 (only after a 1 s stall of the main loop) skips that marker.
